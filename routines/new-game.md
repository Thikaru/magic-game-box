# ルーチン①: 本日のゲームを新規作成（改訂版 v2）

- 名前: `本日のゲーム作成`
- トリガー: Schedule — 毎日 6:00（タイムゾーンは Asia/Tokyo になっているか確認）
- リポジトリ: このリポジトリ
- コネクタ: 不要（全部外してよい）

以下をルーチンのプロンプト欄にそのまま貼り付ける。

---

あなたはこのリポジトリの「本日のゲーム」を作成する担当です。
まず CLAUDE.md を読み、規約をすべて守ってください。

あなたの仕事は「無難に遊べる小品を量産すること」ではありません。
**「これは他のどこにもない」と言い切れるコアを1つ持ったゲームを、1日1本作ること**です。
そのために、実装の前に必ず**設計書（ブループリント）を書き、それを `blueprints/` に
保存してから**コードを書き始めてください。

---

## 手順

### 1. 日付確認

`TZ=Asia/Tokyo date +%Y-%m-%d` で今日の日付を確認する。

### 2. 重複チェック

`games.json` を読む。今日の日付のゲームがすでに存在する場合は何もせず終了する。
`routines/games-log.md`（制作記録）と `blueprints/` 内の過去の設計書を読み、
これまでのコンセプト・コアメカニクス・題材を把握する。

### 3. 発想フェーズ（3案出して1案を選ぶ）

`games.json` の**前日（直近1件）**のジャンルと同じジャンルは選ばない
（直近7件全体との重複は気にしなくてよい）。

後述の【ジャンル/軸リスト】から、**「メカニクス軸」から1つ以上 + 「制約・仕掛け軸」
から1つ以上**を必ず掛け合わせ、さらに題材・感情を足して**コンセプトを3案考える**。
リストは発想の起点であって檻ではない。リストにない新しい遊び方を思いついたなら
それを最優先で採用してよい。

3案それぞれについて、次の1文を書けるか試す：

> 「これは、**〈誰〉**が、**〈どの瞬間〉**に、**〈どんな感情〉**を味わうゲームである。
> 既存の〈類似作〉と違うのは、**〈たった1つのコア〉**があるからだ。」

この1文が書けない案は却下する。3案とも書けないなら発想からやり直す。
書けた案の中から、**「一番説明が短くて、一番驚きが大きいもの」**を1つ選ぶ。
「どこかで見た構成」「ジャンル名を言えば中身が全部わかるもの」は選ばない。

### 4. 設計書（ブループリント）を書いて保存する ★必須

`blueprints/YYYY-MM-DD-<slug>.md` を作成し、以下のテンプレートをすべて埋める。
**ここを埋め切れないまま実装に進んではいけない。**
埋めようとして手が止まる項目があるなら、それはコンセプトがまだ弱い証拠なので
手順3に戻る。

```markdown
# <ゲームタイトル>  (YYYY-MM-DD / slug)

## 1. ワンライン
（1文。これを読んだだけで遊びたくなるか？）

## 2. コアメカニクス（1つだけ）
これを取り除いたらゲームが成立しなくなる中心の仕組みを1つだけ書く。
2つ以上書きたくなったら、それはコアが定まっていない。

## 3. 新規性 — どこが「他にない」のか
- 掛け合わせた軸: 〈メカニクス軸〉×〈制約・仕掛け軸〉（+題材）
- 一番近い既存ゲーム: 〇〇
- それと決定的に違う点: 〜
- 過去作（games-log.md / blueprints）との差分: 〜
- 【却下チェック】ジャンル名だけで中身が説明できてしまわないか？ → No であること

## 4. 心が震える瞬間（最重要）
- 対象プレイヤー: どんな人か（例: パズルは苦手だが手癖でうまくなる感覚が好きな人）
- 狙う感情を**1つに絞る**: 例）「してやられた」「間に合った」「気づいてしまった」
  「もったいない」「自分が上手くなった」「静かで心地よい」
- その感情が発火する**具体的な瞬間**: 例）残り0.3秒で最後の1個が繋がった瞬間
- なぜ震えるのか（設計上の理由）: 例）直前まで失敗が確定していたと錯覚させているから
- この瞬間を**確実に起こすための仕掛け**: 〜

## 5. 体験フロー（時間で設計する）
- 0〜10秒: 何が起きて、操作方法をどう理解させるか（説明画面は読まれない前提）
- 10〜60秒: プレイヤーが習得する「最初のパターン」は何か
- 1〜3分: そのパターンをどう裏切る／深めるか（＝飽きが来る前の変化）
- 終了時: どんな気持ちで「もういちど」を押すのか

## 6. 学習の階段（Koster: 面白さ＝学習）
プレイヤーが順に習得するパターンを箇条書きで列挙する（3〜5個）。
最後に「習得し切った後に何が残るか」を書く（スコア更新／新しい崩し方の発見 など）。

## 7. 意味のある選択（Sid Meier）
プレイヤーが繰り返し迫られる選択と、そのトレードオフを書く。
「常に正解の選択肢」が存在していないことを確認する。
（反射神経系なら「どのリスクを取るか」を必ず用意する）

## 8. 難易度カーブ（数値で書く）
| 経過 | 速度/出現間隔 | 追加要素 | 想定生存率 |
|---|---|---|---|
| 0-30秒 | | | |
| 30-60秒 | | | |
| 60-120秒 | | | |
| 120秒- | | | |
- 緊張と緩和の波をどこに置くか: 〜
- 上達を可視化する仕掛け（自己ベスト、前回記録との比較など）: 〜

## 9. フィードバック設計（ジュース）
- 視覚: 画面揺れ / パーティクル / イージング / 色の変化
- 音: Web Audio API で鳴らす効果音とBGM（音が核となるジャンルなら必須）
- 「気持ちよさ」の中心になる1つの演出: 〜

## 10. 失敗の納得感
- 負けた瞬間、プレイヤーは何を見て「自分のミスだ」と理解するか
- 理不尽（予告なしの即死、隠れた乱数での敗北）が起きないことの確認
- 「惜しい負け」を意図的に作る仕掛け: 〜

## 11. 非目標（作らないもの）
スコープを守るために、あえて実装しないものを列挙する。

## 12. 検証ポイント（セルフレビューで確認する項目）
- [ ] 10秒で操作が理解できる
- [ ] 3分遊んだ人が友達に一言で説明できる
- [ ] 負けた理由が本人にわかる
- [ ] 2回目のプレイに前回と違う体験がある
- [ ] 「4. 心が震える瞬間」が実際にコード上で起こりうる
```

### 5. 実装

`games/YYYY-MM-DD-<slug>/` フォルダを作成し、`index.html`（+必要なら `game.js`）と
`meta.json` を実装する。**設計書に書いた内容から逸れないこと**（逸れる場合は設計書も
更新して整合させる）。

CLAUDE.md の必須要件（説明画面から開始 / もういちどボタン / トップへ戻るリンク /
外部依存なし / タッチとキーボード両対応 / 音が核となるジャンルなら Web Audio API での
効果音・BGM）を必ず満たすこと。
見本として `games/2026-07-07-block-breaker/` の構造を参考にしてよい。

難易度は「初見で1〜3分遊べて、少し悔しくてもう1回押したくなる」程度に調整する。
固定難易度にはせず、**時間経過・スコア・レベル/ラウンド進行のいずれかに応じて
段階的に難しくなる**カーブを必ず組み込む。
説明画面には操作方法・勝利条件・注意点を具体的に書く
（「〜だけ」「たまに〜」のような曖昧な説明で終わらせない）。

### 6. セルフレビューと修正

実装が一通り終わったら、一度実装者の視点を離れてコードを読み直し、
**設計書の「12. 検証ポイント」を1項目ずつ照合**しながら、以下を確認してその場で修正する。

- コンセプト達成度: 設計書の「心が震える瞬間」は、実際にこのコードで起きるか。
  起きないなら、その瞬間が起きるように数値や演出を作り直す。
- 難易度カーブ: 序盤が簡単すぎないか / 終盤まで単調でないか。設計書の表の
  想定生存率に近づくまで数値（速度・出現間隔・敵の量など）を調整する。
- バグ・詰み: 操作不能、判定のすり抜け、無限ループ、スコア異常などがないか。
  説明画面→プレイ→ゲームオーバー/クリア→もういちど、を最初から最後まで
  コードレビューでトレースする。
- 説明文の分かりやすさ: 初見のプレイヤーが読んだだけで「何をすればいいか」を
  理解できるか。
- ジュース: 入力に対して画面と音が即座に反応しているか。無反応な操作がないか。

問題が見つかった場合は修正し、直した内容が新たなバグを生んでいないか
もう一度確認する。修正の結果コンセプトが変わったら設計書も更新する。

### 7. 記録の更新

- `games.json` の先頭に新しいゲームを追加する（既存エントリは変更しない）。
- `routines/games-log.md` に1行追記する（日付・ID・ジャンル/掛け合わせた軸・
  コアメカニクス・狙った感情の要約）。

### 8. 品質チェック

- `python3 -m json.tool games.json` が成功すること
- `node --check` で JS の構文エラーがないこと
- 開始→プレイ→終了→リトライの流れをコードレビューして論理的に確認すること
- `blueprints/YYYY-MM-DD-<slug>.md` が存在し、テンプレートの全項目が
  埋まっていること

### 9. PR 作成

`claude/game-YYYY-MM-DD` ブランチにコミットし、
PR タイトル `game: YYYY-MM-DD <ゲームタイトル>` で PR を作成する。
PR 本文には次を書く：

- ワンライン（設計書の1.）
- コアメカニクスと、それが「どこが他にないのか」
- **どんな人の心が、どの瞬間に、どう震えるのか**
- 操作方法
- 難易度カーブの概要
- セルフレビューで直した点

**成功条件**: 新しいゲームフォルダ・`blueprints/` の設計書・`games.json`・
`routines/games-log.md` の更新だけを含む PR が1つ作成されていること。
それ以外（index.html / archive.html / assets / 過去のゲーム / CLAUDE.md）は
一切変更しないこと。`blueprints/` フォルダが存在しない場合のみ、新規作成してよい。

## 【面白さの指針 — 研究・定説からの設計原則】

設計書と実装は、以下の原則に照らして判断すること。
迷ったときは「この変更はどの原則を強めるか」を自問する。

1. **フロー理論（Csikszentmihalyi）**
   人は「挑戦」と「自分の技能」が釣り合っているときに最も没入する。
   簡単すぎると退屈、難しすぎると不安。さらに、明確な目標と即時フィードバックが
   没入の条件になる。
   → 難易度は「プレイヤーの上達より、ほんの少しだけ速く」上げる。
   常に「今何をすべきか」が画面上でわかるようにする。

2. **面白さ＝学習（Raph Koster『A Theory of Fun』）**
   楽しさの正体は、脳がパターンを習得する快感。パターンを習得し切った瞬間に
   飽きが来る。
   → 3分のプレイの中に「新しい発見」を最低2回仕込む。
   設計書の「6. 学習の階段」がこの原則の具体化である。

3. **意味のある選択（Sid Meier）**
   ゲームとは一連の興味深い選択である。
   → どの選択肢にも利点と代償があり、「常に正解の選択」が存在しないようにする。
   選択のない反射神経ゲームにするなら、代わりに「どのリスクを取るか」を作る。

4. **内発的動機の要素（Malone 1981 / Malone & Lepper 1987）**
   挑戦・好奇心・空想・コントロールが、遊び続けたい気持ちを生む。
   好奇心には「感覚的好奇心（見た目・音の心地よさ）」と
   「認知的好奇心（知識の穴を埋めたい）」がある。
   → 「あと少しで全体像が見えそう」という不完全さを意図的に残す。

5. **自己決定理論 / PENS（Ryan, Rigby & Przybylski 2006）**
   有能感・自律性・関係性が満たされるゲームほど楽しさと継続が高い。
   → **有能感**（上達が実感できる）と**自律性**（自分で選んだ感覚）を必ず設計する。
   自己ベスト表示、直前プレイとの比較、複数の攻略ルートが具体策。

6. **4 Keys 2 Fun（Nicole Lazzaro）**
   楽しさには、ハードファン（達成・克服）、イージーファン（好奇心・探索）、
   シリアスファン（リラックス・没入・気分の変化）、ピープルファン（他者との関わり）
   がある。
   → **どれを主軸にするかを1つ決める**。全部を狙うと何も残らない。

7. **MDA フレームワークの「8つの楽しさ」（Hunicke, LeBlanc & Zubek 2004）**
   感覚 / 空想 / 物語 / 挑戦 / 交流 / 発見 / 表現 / 日課。
   → 主軸を2つまで選び、設計書に明記する。
   また MDA の要点は「メカニクス（ルール）→ダイナミクス（実際の挙動）→
   エステティクス（感情）」の順に効果が伝わること。
   狙う感情から逆算してルールを決める。

8. **ゲームフィール / ジュース（Steve Swink『Game Feel』、"Juice it or lose it"）**
   同じルールでも、入力への即時かつ過剰な反応があるだけで体感は別物になる。
   → 画面揺れ、パーティクル、イージング、スケールの弾み、効果音の重ね、
   ヒットストップ。**無反応な入力を1つも残さない。**

9. **Bushnell's Law（学ぶのは易しく、極めるのは難しい）**
   → 操作は1〜2種類に絞り、深さはルールの組み合わせで出す。

10. **失敗の納得感（フェアネス）**
    「自分のミスだ」と思えれば再挑戦し、「理不尽だ」と思えば離脱する。
    → 予告なしの即死、見えない乱数による敗北を禁止する。
    危険は必ず事前に画面上で予告する。

11. **ニアミス効果 / ツァイガルニク効果**
    「あと少しだった」体験と、中断された課題は強く記憶に残り、再挑戦を促す。
    → 残り1体、残り0.2秒、あと1マス、といった「惜しい負け」が
    自然に発生する数値設計にする。結果画面で「あと〇〇」を明示する。

12. **緊張と緩和のリズム（Yerkes-Dodson の逆U字）**
    覚醒度が高すぎても低すぎても成績と快感は落ちる。
    → 常時最大負荷にしない。ウェーブ間の小休止、静かな数秒を挟み、波を作る。

13. **認知負荷と、遊ばせながら教える設計**
    新要素は一度に1つずつ。説明文は読まれない前提で組む。
    → 最初の10秒は「失敗しても損しない安全な場所」で、操作が自然に分かる状況を作る。
    説明画面は「読めば分かる」ではなく「読まなくても分かる」設計の補助と位置づける。

14. **変動報酬は使ってよいが、搾取しない**
    ランダム性は驚きを生むが、引き延ばしや射幸性の道具にしない。
    → 1〜3分で完結し、運より腕前が結果を左右する配分にする。

15. **上達の可視化**
    人は「自分が上手くなった」と感じられるときに最も強く続けたくなる。
    → スコアだけでなく、自己ベスト、到達段階、前回との差分を必ず見せる。
